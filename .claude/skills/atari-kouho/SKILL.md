# 当たり候補 自動判定（atari-kouho）

CR停止判定（ネガ側）のポジ版。**CPAが目標を下回る好調CRを自動で光らせる**仕組みを
集計表に入れる。セッション環境に Google 認証は無いため、読み書きはすべて
GitHub Actions（`ymd0726/test`）経由で行う。

## 1. 仕様（確定済み・勝手に変えない）

### 表示位置
- **消化金額列**（＝当たり判定プルダウンと同じ列）の **2行目**
- 2行目は各ブロックで `-` プレースホルダが入っているのでそこを置き換える
- プルダウン（5行目）には**絶対に触れない**。判定は表示専用

### 2段階（段階は新芽の数で表現。「予備軍」「🔥」「狼煙」は廃止語）
| 段階 | ラベル | 条件 |
|---|---|---|
| 1段階目 | `当たり候補🌱` | CPA ≤ 目標CPA×`data!S2` かつ 実質cv ≥ `data!S3` |
| 2段階目 | `当たり候補🌱🌱` | CPA ≤ 目標CPA×`data!S4` かつ 実質cv ≥ `data!S5` |

共通の前提ゲート: `消化金額 ≥ 目標CPA × 消化ライン`（データ量が足りないCRは点灯させない）

**必ず目標CPAを下回る時だけ点灯させる。** 係数を1.0超にすると目標より悪いCRが光るので不可。
量が多いだけの「量型」は対象外（CPA効率重視、というのがユーザーの明示的な判断）。

### 判定基準は data シートで編集可能にする
`data!R1:R5` にラベル、`data!S2:S5` に数値を置く。式はこのセルを参照するので、
**基準変更はシート上の数値編集だけで全CRに即反映**（ツール再実行は不要）。

| セル | 内容 | jde での値 |
|---|---|---|
| S2 | 🌱 CPA係数（目標CPA×） | 0.9 |
| S3 | 🌱 実質cv下限 | 3 |
| S4 | 🌱🌱 CPA係数（目標CPA×） | 0.75 |
| S5 | 🌱🌱 実質cv下限 | 5 |

### 親子対応
親（子有り）は自身の指標が「子にて判定」で使えない。
**配下の子に1つでも該当があれば親にも表示**する（上位段階を優先）。

## 2. 式の設計（★ここが肝。崩さない）

**全ブロックで式は完全に同一**にする。親用・子用を書き分けない。
理由: CRは cr00 の列群を複製して増やすため、式がブロックごとに違うと
**追加のたびにツール再実行が必要**になってしまう（ユーザーからの明確な要求）。

そのために2つの仕掛けを使う:

### (a) 子の探索を式の中で動的に行う
親かどうかを事前判定せず、`COUNTIF` で「自分のID + `_*`」に一致するブロックを数える。
いれば子を集約、いなければ自分の判定を使う。**子を後から足しても親の式は書き換え不要**。

### (b) 中間行を挟んで循環参照を回避
表示行（2行目）で子を集約すると、子の表示セルも2行目にあるため循環参照になる。
判定結果を数値 0/1/2 で持つ**中間行**（例: 1103行目）を挟む。

```
中間行（1103行目・全ブロック同一）: 自分の指標だけで 0/1/2 を返す。他ブロックを参照しない
=IF(N(AI1101)<$W$5*$W$3,0,
  IF(AND(ISNUMBER(AQ1101),AQ1101<=$W$5*data!$S$4,N(AO1101)>=data!$S$5),2,
  IF(AND(ISNUMBER(AQ1101),AQ1101<=$W$5*data!$S$2,N(AO1101)>=data!$S$3),1,0)))

表示行（2行目・全ブロック同一）: 子がいれば子の中間行を集約、いなければ自分の中間行
=LET(id,AI6,kids,COUNTIF($6:$6,id&"_*"),
  t,IF(kids>0,
      IF(COUNTIFS($6:$6,id&"_*",$1103:$1103,2)>0,2,
      IF(COUNTIFS($6:$6,id&"_*",$1103:$1103,1)>0,1,0)),
      N(AI1103)),
  IF(t=2,"当たり候補🌱🌱",IF(t=1,"当たり候補🌱","")))
```

- 列参照（`AI6` `AI1103` `AI1101` `AQ…` `AO…`）はすべて**相対** → 列複製で自動追随
- `$6:$6` `$1103:$1103` `$W$5` `data!$S$2` は**絶対** → 全ブロック共通
- cr識別子は消化金額列と**同じ列**のID行にある（この前提が崩れると式が壊れる）
- 中間行は表示行が保護されたCRにも入れる → 手動注記があるCRも親の集約には効く

## 3. 横展開の手順

### Step 1: 対象タブの実測（思い込みで書かない）
`inspect-sheet.yml` を dispatch して以下を確定させる。

| 確認項目 | 確認方法 | jde の実例 |
|---|---|---|
| 目標CPAセル | 停止判定式（5行目等）が参照している `$W$5` 等 | W5 |
| 消化ラインセル | 同上の `$W$3` 等 | W3 |
| **指標行** | 停止判定式が参照している行番号。**タブごとに違う** | mak=1100 / kou=1101 |
| ID行 | 構造ダンプの「クリエイティブID行」 | 6 |
| 表示行2の中身 | `rows=2, formulas=true` でダンプ | `-` と手動注記が混在 |
| 中間行の空き | `cells=AI1103,EQ1103,…` で複数ブロックを抜き取り | 1103が空（1102は実データ） |

指標行を間違えると全CRが誤判定になる。**必ず既存の停止判定式から読み取る。**

### Step 2: dry-run
`noroshi.yml` を dispatch（`mode=dry-run`）。inputs は Step 1 の実測値。

ログで必ず確認する:
- `実CRブロック（当たり判定対象）` の件数が妥当か
- `中間行 NNNN: 全 N ブロックで書込可` … **非空があると中止する**。出たら別の空き行を選ぶ
- `表示行 2 に保護対象の内容があるため表示は見送り` … 手動注記（`エリア` `NG素材` 等）。
  これは**壊さないのが正解**。件数と中身をユーザーに報告する
- 点灯予測が実感と合うか（既知の当たりCRが光るか、目標CPAより悪いCRが光っていないか）
- 生成式が親・子で同一になっているか

### Step 3: apply
`mode=apply` で再 dispatch。`要目視確認 0 件` を確認。
undo ログがアーティファクト `noroshi-undo-log` に90日保存される。

### Step 4: 報告
書込セル数・点灯中のCR・保護したセル・undoログの場所をユーザーに伝える。

## 5. 安全策（実装済み。無効化しない）

- dry-run がデフォルト。`apply` 時のみ書き込み
- 表示行は「空 / `-` / 既存の当たり式」のみ上書き。**手動注記は保護して除外**
- 中間行は「空 / 既存の中間式」のみ。他の内容があれば**書き込まず中止**
- 5行目のプルダウンには一切触れない
- 書き込み前に undo ログ、書き込み後に再読取で全セル照合
- 既存の当たり式は上書き更新されるので、基準やラベルの変更は再実行で反映できる
