## 3. 拡張候補の提案（ページがよく溜まるDB）

優先度順。いずれも**未実装**であり、採用可否は要判断。

### ① 社内MTGDB（最優先・推奨）
`collection://ffe36162-7df0-4dfc-a886-919b18bcd7e2`
- 週次で確実に増える現役DB。週次運用共有会＝社内の意思決定・課題が最も濃い場所。
- 取り込み先は 🏢社内コンテキストDB（スコープ＝社内）。
- ⚠️ **実装上の注意**: このDBには `コンテキスト抽出済み` フラグが無い。
  同名プロパティを追加するか、`発生日` / `Created time` ベースの差分判定＋
  生ログ層の `ソースURL` 突合で重複回避する必要がある（実装方式の決定が必要）。

### ② 決定ログDB / 決定事項DB
`collection://0f1f1f04-4138-4421-a46b-54ff85ec122b`
- 議事録&施策DB の `決定事項` / `決定ログ` relation 先。意思決定が構造化されて溜まる。
- 集約層の「3.意思決定」を直接埋められるため、要約の質が上がりやすい。
- 議事録経由で間接的に拾えている可能性があるため、**重複の出方を先に確認**すべき。

### ③ 論点・課題DB
`collection://257fa44f-1b1e-4ffe-901d-e2d4eef1b177`
- 議事録&施策DB の `論点・課題` relation 先。
- 集約層の「5.論点・課題・リスク」と TOOL-15 の課題フラグ管理に直結する。

### ④ 目標・OKR DB
`collection://7e7441fc-f6b3-4d60-baee-7ae333570e72`
- 集約層の「4.目標KPI/OKR」の材料。更新頻度は四半期単位で低いため、
  日次クロールより**週次🅲での参照**が費用対効果が良い可能性が高い。

### 非推奨
- **ワークDB**（`collection://5f92b1c7-...`）: 研修コンテンツ台帳であり、
  意思決定・期限付きタスクが溜まらない。通知ノイズを増やすだけになりやすい。
- **ナレッジDB / DB置き場db**: ストック情報であり日次の差分がほぼ無い。

## 4. 拡張するときの共通チェックリスト

新しいDBを取り込み対象に追加する場合、以下を必ず設計してから実装する。

1. **重複防止**: `コンテキスト抽出済み` 相当のフラグを足すか、日付＋`ソースURL`突合にするか。
2. **スコープ判定**: 📋案件（CLDB紐づき/案件コード）と 🏢社内 のどちらへ入れるか。
3. **件数上限**: 🅰は1回最大10件程度で回している。対象を増やすなら上限配分を見直す。
4. **通知への波及**: 生ログの `種別=タスク` かつ `期限` 付きは 🅱 の Slack 通知に載る。
   期限を持つレコードが大量に増えるDBを足すと通知ノイズが跳ねるため事前に見積もる。
5. **初回バックフィル**: 過去分をどこまで遡るか（全件だと🅰が1回で終わらない）。
