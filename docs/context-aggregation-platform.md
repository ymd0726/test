# 議事録を毎日コンテキスト化する基盤（TOOL-14）仕様書

> 着想元: Notion「【アイデア】議事録を毎日コンテキスト化する基盤」(`38535c2adb56810fab9fdf981dcdc742`)
> 本命の下流: TOOL-15「コンテキスト連携タスク・課題フラグ管理」(`38535c2adb5681598d7cfd8b08e67a9c`)
> 実装方針はリポジトリで版管理し、実データ・実行成果物はNotionに蓄積する。

## 1. 目的とスコープ
点在する議事録・Slack・朝礼・1on1の情報を毎日自動でコンテキスト化し、
「案件/テーマごとに育つ集約コンテキスト」を最新化し続ける基盤。
下流ツール（最初はタスク期限のSlack通知、将来は施策提案・1on1アシスト）の共通インプットになる。

## 3. アーキテクチャ（2層モデル）
```
ソース（議事録&施策DB / Slack全ch / 朝礼 / 1on1）
   │  ① 取り込み（差分のみ：コンテキスト抽出済み=NO の議事録・昨日のSlack）
   ▼
[生ログ層] 既存 📋案件 / 🏢社内 コンテキストDB（追記型・1レコード=1トピック・既存スキーマ流用）
   │  ② 差分マージ（当日 抽出日 が新しい生ログを案件/テーマ別に束ね、該当集約だけ更新）
   ▼
[集約層・新設] 🆕 集約コンテキストDB（案件/テーマ単位・構造化セクション・最新上書き＋変更ログ）
   │  ③ 下流活用
   ▼
タスク期限 → Slack通知（TOOL-15の起点）／将来：施策提案・1on1アシスト
```

## 4. 集約コンテキストDB（新設）設計

### プロパティ
| プロパティ | 型 | 説明 |
|---|---|---|
| `Name` | title | 案件名 or テーマ名 |
| `スコープ種別` | select | 案件 / テーマ |
| `案件` | relation→CLDB(`6ca19ba4...`) | 案件スコープ時のみ |
| `状態` | select | 進行中 / 休眠 / 完了（鮮度把握・最小限） |
| `重要フラグ` | multi-select | 重要課題 / 悩み中 / 要決定（TOOL-15の種） |
| `最終更新日` | date | 差分マージで更新 |
| `生ログ` | url（or relation） | 生ログ層レコードへの参照 |

### ページ本文＝構造化セクション（固定見出し）
1. **サマリー（最新状況）** — 3〜5行
2. **背景・経緯**
3. **意思決定・決定事項**
4. **目標・KPI/OKR**
5. **論点・課題・リスク**（重要フラグ付き）
6. **タスク・期限**（`- [ ] タスク / 担当 / 期限YYYY-MM-DD / ソースURL`）
7. **関係者**
8. **変更ログ** — 日次1行追記: `YYYY-MM-DD: <更新要点>`

### 運用ルール（既存踏襲）
- ノーレビュー原則（自動更新前提、人手レビューなし）
- 本文中 @メンション禁止（URL文字列のみ）
- 重複防止（同一トピックの二重記載を避ける）
- 失敗時は保存せず、理由と不足情報を出力
- 履歴は「最新上書き＋変更ログ追記」。本文は常に最新状態を表す。

## 5. 日次パイプライン（定時トリガー本体プロンプトの仕様）

1本の定時トリガーで以下を順次実行（旧 03:00/03:30 の役割を統合・復活）。

### ① 取り込み（差分のみ）
- 議事録&施策DB から `コンテキスト抽出済み = __NO__` のレコードを取得
- 各議事録本文/`AI要約`/`MTG要約` から 決定事項・論点課題・目標・タスク・リスク・メモ を抽出
- スコープ判定（`Tags`=🗣️社内MTG → 社内、`CLDB`紐付き/案件コード → 案件）して生ログ層2DBへ登録
- Slack: 昨日分の全公開ch更新を要約し、`ソース種別=Slack`・`[Slack]`プレフィックスで生ログ層へ
- 取り込み済み議事録は `コンテキスト抽出済み = __YES__` に更新（再処理防止）

### ② 差分マージ（集約層を育てる）
- 当日 `抽出日` が新しい生ログを `案件` / テーマ別に束ねる
- 対象の集約レコードを取得（無ければ新規作成）
- 新規生ログを該当セクション（決定/目標/課題/タスク等）へLLMでマージ → 本文を上書き
- `変更ログ` に1行追記、`最終更新日` を更新
- **触れた案件/テーマだけ処理**（アクティブ10〜30件想定でも低コスト・冪等）

### ③ 下流通知（タスク期限 → Slack）
- 集約DBの「タスク・期限」/生ログのタスク種別から `期限` 付きを抽出
- 期限が「閾値以内（例: 3日以内）」または「超過」を案件横断で集約
- 「今日の要対応」を1メッセージにまとめてSlackの指定chへ通知

## 6. 実行基盤
- **Claude Code（web）の定時トリガー**で毎日起動（例: 04:00 JST）
- MCP経由で Notion / Slack を読み書き
- まず手動 fire でドライラン → 出力安定を確認後にスケジュール有効化

## 7. 検証手順
1. 集約DB単体: 1案件で手動マージ → 構造化セクションが埋まり変更ログが追記されるか
2. 冪等性: 同日2回実行で二重記載・崩れが出ないか
3. 下流通知: 期限テストレコードでSlack通知が正しく出るか（手動 fire）
4. 定時トリガー: ドライラン1〜2日 → 安定後にスケジュール有効化
5. コスト: 触れた案件/テーマのみ処理されているか
